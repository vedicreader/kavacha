build

Build the app: find a Python py2app can use, install pinned packages, run the freezer, and record the commit it came from

This module runs a build. A Mac build has requirements that are easy to get wrong: py2app needs a framework build of Python, the bundle should contain the exact package versions in uv.lock, and a build must not overwrite an app that is running. Afterwards you want to know which commit an app came from. check reports on all of this without changing anything, and build does the work.

lock_requirements

def lock_requirements(
    root, extras:tuple=(), out:NoneType=None
):

Export the uv.lock in root as a pinned requirements file and return its path, or None if that is not possible.

A bundle should contain the package versions your project was tested with. lock_requirements asks uv to export the uv.lock in root as a pinned requirements file, including the optional dependency groups named in extras, and writes it to out, by default packaging/.app-venv/app-requirements.txt. It returns the file’s path, or None when there is no uv.lock or the export fails. build_venv takes None to mean that it should install from pyproject.toml instead, with whatever versions pip picks.

tmp = TemporaryDirectory(); root = Path(tmp.name)
lock_requirements(root) is None
True

build_venv

def build_venv(
    python, venv, root, extras:tuple=(), force:bool=False
):

Create or update the build venv at venv from python, install the project with pinned requirements, and return its Python.

build_venv prepares the environment a macOS build runs in. It creates a virtual environment at venv from the interpreter python, starting again if force is set or if the existing one was made with a different Python version. It installs the pinned requirements from lock_requirements when there are any, installs the project at root in editable mode with its extras, and returns the path of the environment’s Python. build calls it. It has no example here because it installs packages.

git_stamp

def git_stamp(
    root, version:str=''
):

Return the commit, dirty flag, version and build time for the checkout at root, or None outside one.

A bundle is a copy of your code, and nothing in it says which version of the source it came from. A stamp records that. It is a small JSON file named build.json (the name is in STAMP) that holds the git commit, whether the checkout had uncommitted changes, the version and the build time.

stamp_path says where the stamp goes: inside Contents/Resources for a .app, and next to the executable for anything else. It decides by the .app suffix alone, so it works for a bundle that has not been built yet.

stamp_path('/dist/Demo.app'), stamp_path('/dist/Demo')
(Path('/dist/Demo.app/Contents/Resources/build.json'),
 Path('/dist/Demo/build.json'))

git_stamp collects the stamp’s fields from the git checkout at root, or returns None if root is not in one. write_stamp writes the stamp into a bundle and returns it. Outside a checkout the commit is left empty, and if the bundle’s folder does not exist nothing is written. read_stamp reads the stamp back, and returns None if the bundle has none or it cannot be parsed.

st = write_stamp(repo/'dist'/'Demo.app', repo, version='2.0.1')
st['commit'][:12], st['dirty'], st['version']
('3b2bbb3a952a', False, '2.0.1')
read_stamp(repo/'dist'/'Demo.app') == st
True

If tracked files have changes that are not committed, the stamp says dirty, and build prints that next to the commit. When an app misbehaves, you can then tell whether it was built from code that was never committed.

(repo/'x.txt').write_text('changed')
git_stamp(repo)['dirty']
True

check

def check(
    spec, root, venv:NoneType=None
):

Report what a build would do on this machine without doing it; works on any platform, Linux included.

check reports what build would do on this machine, as a dict, without building anything or changing any files. It names the platform, the interpreter and the freezer, says whether pywebview is installed, and lists the process IDs of any running copies of the app. On macOS it also says whether the current Python is a framework build and, if it is not, which framework Python and which build environment build would use instead. On Linux it says that nothing can be built there: a Mac app is built on macOS and a Windows app on Windows. Run it first when a build fails before it starts. The example replaces two machine-specific paths in the result.

demo = App(name='Demo', entry='demo_app.py', version='2.0.1')
rep = check(demo, repo)
{**rep, 'interpreter': '/proj/.venv/bin/python3', 'out': '/proj/dist/Demo'}
{'platform': 'linux',
 'interpreter': '/proj/.venv/bin/python3',
 'app': 'Demo',
 'out': '/proj/dist/Demo',
 'freezer': 'none — linux builds nothing; macOS and Windows build on their own OS',
 'pywebview': 'MISSING',
 'running': []}

build

def build(
    spec, root, setup_py, venv:NoneType=None, alias:bool=False, force:bool=False, rebuild_venv:bool=False,
    identity:NoneType=None
):

Freeze spec into root/dist, switching to a framework Python first on macOS when needed.

build freezes spec into root/dist and returns the path of the result. setup_py is the script that calls the freezer for your app. It will not start while a copy of the app is running, unless you pass force=True, because the build replaces the standard library the running app imports from, and that app then fails with a zip error that says nothing about the build.

On macOS it next checks the interpreter. If the current Python is not a framework build, build finds one with framework_python, prepares an environment with build_venv (pass rebuild_venv=True to make it from scratch), runs the script that called build again with that environment’s Python, and returns. The environment variable KAVACHA_BUILD_VENV (the name is in REEXEC) marks the second run, so a Python that is still unsuitable stops the build instead of looping.

On a framework Python, and on Windows, it runs the freezer, calls finish on macOS with identity, writes the stamp, and prints where the app is and which commit it was built from. alias=True asks py2app for an alias build, which refers to your source files instead of copying them and is quicker while you develop.
